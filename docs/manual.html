1What Bluewright is

When you investigate a new feature, the work rarely moves in a straight line. You gather requirements, look at what already exists, weigh approaches, sometimes build a quick proof of concept, share drafts, absorb feedback — and meanwhile other teams keep changing the systems you're designing against.

Bluewright gives that work a home. It's a set of /bluewright:* commands for Claude Code that keep one folder per investigation: your inputs, your decisions, your open questions, your to-do list, your experiments, and the polished artifacts you share with others. Nothing lives in Claude's memory or in hidden state — everything is plain markdown and YAML in a git repository you own.

The end product of an investigation is a solution design: a document (plus diagrams) you can present to your team and cut implementation tickets from, where every claim traces back to a recorded decision, a spike result, or a requirement.

2How it thinks — four ideas

Workspace

A workspace is a folder (and git repo) for one product or team. You can have several. It's marked by a workspace.yml file that stores team-wide defaults — Jira project keys, a Confluence space, systems worth watching — so each new investigation starts pre-configured. A KNOWLEDGE.md index at the top links every investigation and collects facts about your systems that outlive any single feature.

Investigation

An investigation is one feature question, in one subfolder of the workspace. Everything about it lives there:

my-workspace/
  workspace.yml            ← marks the workspace, holds team defaults
  KNOWLEDGE.md             ← index across all investigations
  payments-split/          ← one investigation
    investigation.yml      ← phase, links, watchlist
    inputs/                ← requirements, samples, anything you collect
    decisions.md           ← the decision log
    questions.md           ← open questions
    todo.md                ← prioritized next steps
    sync-log.md            ← trail of external-change checks
    spikes/                ← proof-of-concept experiments
    outputs/               ← what you share with others

The four living files

Feedback and outside changes arrive whenever they want, so four files stay alive through every phase and every command reads and updates them:

  • decisions.md — every choice made, numbered D-001, D-002… Append-only: a wrong decision is superseded by a new entry, never erased. This is your investigation's memory.
  • questions.md — everything still unsettled, numbered Q-001… with a note on what each question blocks.
  • todo.md — prioritized into Now / Next / Later / Done, numbered T-001…
  • the watchlist (inside workspace.yml and investigation.yml) — the repos, Jira queries, and Confluence pages whose changes could invalidate your work.

Outputs are the only shareable surface

Only outputs/ ever leaves the workspace. It's built to be self-contained: send the folder to a colleague and everything — the brief, the option comparison, the design, rendered diagrams — reads correctly with no other context.

3Getting started

Install once

/plugin marketplace add valeriy-maslov/bluewright
/plugin install bluewright@bluewright

Restart Claude Code (or open a new session) so the plugin loads.

Create a workspace, then an investigation

/bluewright:init ~/work/my-team        # once per product/team
cd ~/work/my-team
/bluewright:new payments-split         # once per feature

Both commands ask a few short questions — every answer except the title is optional and can be edited later in the YAML files. new creates the whole folder structure above and writes everything you told it into inputs/00-intake.md, so nothing said at kickoff gets lost.

Where to run commands Bluewright finds your workspace by walking up from the folder you're standing in — exactly like git finds a repository. Run commands from inside the workspace (or inside a specific investigation), and they know where they are. There is no global registry to configure.

Then: feed it and ask for the brief

Drop whatever you have into inputs/ — requirement docs, meeting notes, diagrams, sample payloads, anything. When there's enough to chew on, run /bluewright:brief.

4The workflow

An investigation moves through five phases. The commands map onto them:

Frame/brief → Options/options → Spike/spike → Share/publish → Design/design

The arrows are the happy path, not a cage: feedback (/capture) and external changes (/sync) can arrive at any moment and legitimately reopen an earlier phase. Not every investigation needs a spike; skip what the work doesn't call for.

A typical run

  1. Frame. /brief reads everything in inputs/, surveys the systems on your watchlist in parallel, and writes outputs/brief.md: numbered requirements (FR-1, NFR-1, C-1), a domain glossary, the current state of each system — and turns every gap or contradiction it finds into a question.
  2. Options. /options first agrees the candidate approaches and judging criteria with you, then researches each candidate in parallel and writes outputs/options.md: a scored comparison matrix and a recommendation, recorded as a proposed decision — accepting it stays your call.
  3. Spike (when needed). /spike kafka-ordering scaffolds a time-boxed experiment tied to one open question. It ends in a written verdict — proven, disproven, or honestly inconclusive. The code is throwaway; the verdict is the deliverable.
  4. Share. /publish renders your PlantUML diagrams to PNG, checks that outputs/ is truly self-contained, marks anything stale, and refreshes a reading-order README. Send the folder, collect feedback, feed it to /capture.
  5. Design. /design checks you're actually ready (approach accepted? blocking questions answered? spikes concluded?), then synthesizes outputs/design.md from the record — and can draft implementation tickets from it.

5Command reference

Grouped by when you reach for them.

Setting up — once each

/bluewright:init <path>

Creates a workspace: workspace.yml, KNOWLEDGE.md, git init. Asks for team defaults; refuses to nest inside another workspace.

/bluewright:new <slug>

Creates one investigation: the folder structure, the four living files, and your kickoff answers preserved in inputs/00-intake.md.

Every day

/bluewright:status

One screen: phase, next tasks, open questions (blocking first), latest decisions, sync freshness — plus flags like "outputs older than your newest decision". Read-only, changes nothing. Start your day here.

/bluewright:capture

The inbox. Paste feedback, a Slack thread, meeting notes — it saves the raw text to inputs/, then routes each item to a decision, question, or task. If feedback contradicts an accepted decision it raises a question and flags it loudly — it never overrules a decision by itself. Use whenever new information arrives, in any phase.

Analysis

/bluewright:brief

Requirements analysis: digests inputs/, surveys watched systems, writes outputs/brief.md, seeds questions from the gaps.

/bluewright:options

Option comparison: candidates and criteria agreed with you first, parallel research per candidate, scored matrix in outputs/options.md, recommendation as a proposed decision.

/bluewright:spike <name>

Time-boxed proof of concept answering exactly one question. The spike folder is the one place where installing and running things is allowed. Always ends in a VERDICT.md.

Watching the outside world

/bluewright:sync

Checks every watchlist entry for changes since the last run — commits in watched repos, updated Jira issues, edited Confluence pages — and answers the question that matters: which of my assumptions moved? Breaking changes raise questions against the affected decisions. Runs unattended, so you can schedule it nightly. Run before big steps, or on a schedule.

Delivering

/bluewright:publish

Makes outputs/ shareable: renders diagrams, verifies nothing links outside the folder, marks stale artifacts honestly, refreshes the README index.

/bluewright:design

The finale: synthesizes outputs/design.md from your decisions, option analysis, and spike verdicts — refusing politely if blocking questions are still open. Offers to draft implementation tickets.

6A worked example, start to finish

A practical lesson with every command in play. The scenario: external subscriber systems must be notified when an order's status changes, within a minute. Your team owns the order service; the API gateway belongs to another team.

Day 1
/bluewright:init ~/work/platform

One-time workspace setup (skip if your team already has one). You give it the team name and Jira project key; it creates workspace.yml and KNOWLEDGE.md and git-inits the folder.

/bluewright:new order-webhooks

You state the goal — "How do we notify subscribers of order-status changes within 60 seconds?" — link the Jira epic, and put two repos on the watchlist: your order-service clone and the other team's api-gateway. Everything you said lands in inputs/00-intake.md. You then drop the integration contract and two meeting notes into inputs/.

Day 2
/bluewright:brief

The inputs are digested and both watched repos surveyed in parallel. Out comes outputs/brief.md: eight functional requirements, three non-functionals (NFR-2: delivery within 60s), two constraints — and two gaps turned into questions: Q-001 "What delivery guarantee do subscribers need?" and Q-002 "Who owns the subscriber registry?".

/bluewright:capture

You paste the product manager's Slack reply. The raw text is saved to inputs/, Q-001 gets its answer (at-least-once is fine, duplicates acceptable), and the registry question becomes a task to chase.

Day 3
/bluewright:options

You confirm three candidates — a polling feed, webhooks from an outbox + queue, a managed event bus — and the criteria, with NFR-2 as a must-have. Three researchers run in parallel; the matrix in outputs/options.md eliminates polling (can't meet 60s at subscriber scale) and proposes D-003: webhooks via outbox. One unknown remains: can order-service emit reliably without a schema change? That becomes a spike task.

Day 4
/bluewright:spike outbox-emit

Scaffolded against that open question with a one-day time-box. Inside spikes/outbox-emit/ you build a throwaway harness against a copy of the schema. Verdict: proven — no schema change needed. The question is answered with the evidence linked; you accept D-003 via /capture.

Day 5
/bluewright:sync

Morning check. The gateway team merged four commits overnight; one renames the event envelope's type field. The impact report says: weakens D-003 — the outbox format assumed the old envelope, and raises Q-004. You re-rule the same day, before the design would have shipped the wrong contract.

Day 6
/bluewright:design

Gates pass: approach accepted, no blocking questions, spike concluded. Out comes outputs/design.md — every section tracing to a decision, verdict, or requirement ID — plus a context and a container diagram, and a draft outputs/tickets.md cut from the design's subsections.

/bluewright:publish

Diagrams render to PNG, links are verified self-contained, outputs/README.md gives the reading order. You send the outputs/ folder to the architects. Their feedback next week? Straight into /capture — the loop is built for it.

Anytime
/bluewright:status

Between all of the above: one screen showing the phase, the top of the to-do list, open questions with blockers first, the latest decisions, and whether anything has gone stale.

7The files, explained

You can open and edit any of these by hand — they're plain text, and the formats are documented in the plugin's docs/spec.md. The essentials:

decisions.md

One entry per decision: context, the choice, its consequences, links to evidence. Append-only — superseding a decision means a new entry pointing back, so the reasoning trail survives. Status moves from proposed to accepted only when you say so.

questions.md

Each question notes who raised it, and what it blocks. Answered questions stay in the file with their answer — they're part of the record.

todo.md

Four sections: Now, Next, Later, Done. Order inside a section is the priority.

inputs/

Anything goes; nothing here is ever shared directly. Captured feedback lands here first, verbatim and dated, before being interpreted.

spikes/<name>/

SPIKE.md states the question, success criteria, and time-box up front; VERDICT.md appears only when it concludes. A spike folder without a verdict is, by definition, unfinished business.

outputs/

Fixed names, so every investigation looks alike: brief.md, options.md, design.md, tickets.md, diagrams as .puml with rendered .png beside them, and a README.md reading guide.

sync-log.md

One dated section per /sync run — including the quiet ones. Your morning-coffee review of what moved overnight.

8Staying current while others ship

The systems you design against don't wait for you. The watchlist plus /sync is Bluewright's answer:

  • Put anything that could move under your feet on the watchlist — a local clone of another team's repo, a Jira query, a Confluence page. Workspace-level entries apply to every investigation; each investigation can add its own.
  • /sync collects what changed since last time, then judges each change against your decisions — not just "4 new commits" but "commit abc123 weakens D-004, which assumed the ledger API is synchronous".
  • It never rewrites your decisions. A broken assumption becomes a flagged question; the re-ruling is yours.
Versions are checked for you Each workspace records the plugin version that created it. A built-in hook checks compatibility on every command — if the plugin is too old for the workspace (or vice versa), you get a clear stop instead of quiet file corruption.

9Ground rules the plugin holds itself to

Your working directory, period

Commands find the workspace by walking up from where you run them. The plugin keeps no global state and never reads or writes outside the workspace — except paths you explicitly put on a watchlist.

Nothing lost, nothing invented

Everything you feed in is preserved verbatim before being interpreted. And no command ever records a decision you didn't make — recommendations arrive as proposed, always awaiting your ruling.

History is append-only

Decision, question, and task IDs are never reused or renumbered. Documents in outputs/ regenerate freely; the record they rest on doesn't move.

Honest artifacts

Publishing marks stale documents instead of quietly rewriting them, and a spike that proved nothing says "inconclusive" — with evidence either way.
