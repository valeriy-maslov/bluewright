Bluewright User Manual

A workspace for capturing what a team knows — an official, workspace-wide record plus per-investigation notes that can graduate into it — and for turning what's captured into answers and artifacts on demand.

1What Bluewright is

Teams accumulate knowledge as they work — decisions made, questions still open, things to do next — and most of it lives nowhere durable: a Slack thread, someone's memory, a doc that drifts out of date. Meanwhile every specific piece of work generates its own version of the same three things, most of which never makes it back to the team's shared understanding.

Bluewright gives that knowledge a home, at two tiers. Global is the workspace's official record — what's actually settled, true for the whole team. Each investigation has its own decisions, questions, and TODOs too, not yet official, but promotable once they prove out. It's a set of /bluewright:* commands for Claude Code; nothing lives in Claude's memory or in hidden state — everything is plain markdown and YAML in a git repository you own.

Once something is captured, two commands work over it: /bluewright:ask to explore the record without changing it, and /bluewright:make-artifact to turn it into whatever you actually need to hand someone — a doc, a diagram, a summary, an email.

2How it thinks — three ideas

Workspace

A workspace is a folder (and git repo) for one product or team. You can have several. It's marked by a workspace.yml file that stores team-wide defaults — systems worth watching by default, such as an issue tracker query or a wiki space — so each new investigation starts pre-configured. A KNOWLEDGE.md index at the top links every investigation.

Global vs. investigation

global/ is the workspace's official record — decisions, questions, and TODOs true for the whole team, not just one feature. An investigation is one feature question, in its own subfolder, with the same three files scoped to just that work. Nothing in an investigation is official until you say so with /bluewright:promote, which copies it into global/ and leaves the original untouched:

my-workspace/
  workspace.yml            ← marks the workspace, holds team defaults
  KNOWLEDGE.md             ← index across all investigations
  global/                  ← the official, workspace-wide record
    decisions.md
    questions.md
    todo.md
    inputs/
    artifacts/
  payments-split/          ← one investigation
    investigation.yml      ← status, links, watchlist
    inputs/                ← requirements, samples, anything you collect
    decisions.md           ← the decision log, scoped to this investigation
    questions.md           ← open questions, scoped to this investigation
    todo.md                ← prioritized next steps, scoped to this investigation
    sync-log.md            ← trail of external-change checks
    artifacts/             ← what you share with others

The living files, at both tiers

global/ and every investigation share one format for three files that both capture commands write to and every other command reads:

  • decisions.md — every choice made, numbered D-001, D-002… Append-only: a wrong decision is superseded by a new entry, never erased.
  • questions.md — everything still unsettled, numbered Q-001… with a note on what each question blocks.
  • todo.md — prioritized into Now / Next / Later / Done, numbered T-001…

Global and each investigation number their own D-/Q-/T- sequences independently — a promoted entry gets a new ID in global/, linked back to its source, never the old one.

Artifacts are the only shareable surface

Only artifacts/ (global or per-investigation) ever leaves the workspace. There's no fixed filename list — /bluewright:make-artifact produces whatever was asked for, self-contained: send the folder to a colleague and it reads correctly with no other context.

3Getting started

Install once

/plugin marketplace add valeriy-maslov/bluewright
/plugin install bluewright@bluewright

Restart Claude Code (or open a new session) so the plugin loads.

Create a workspace, then an investigation

/bluewright:init ~/work/my-team        # once per product/team
cd ~/work/my-team
/bluewright:new payments-split         # once per feature

Both commands ask a few short questions — every answer except the title is optional and can be edited later in the YAML files. init also scaffolds global/; new creates the investigation folder structure above and writes everything you told it into inputs/00-intake.md, so nothing said at kickoff gets lost.

Where to run commands Bluewright finds your workspace by walking up from the folder you're standing in — exactly like git finds a repository. Run commands from inside the workspace (or inside a specific investigation), and they know where they are. There is no global registry to configure.

Then: capture what you know

Paste, point at a file, or just talk — /bluewright:capture-global for anything workspace-wide and official, /bluewright:capture for anything specific to the investigation you're in. Both save what you give them verbatim first, then guide you through which questions or TODOs are actually worth tracking, instead of filing everything they can infer.

4The workflow

There's no fixed sequence of phases — capture, then ask or make an artifact, whenever there's enough to work with:

Capture/capture, /capture-global → Ask/ask / Make artifact/make-artifact → Promote/promote

The arrows are the happy path, not a cage: capture can happen at any moment, in any order, at either tier, and you loop back to it as often as new information arrives. Promotion is optional and only for what's actually proven out.

A typical run

  1. Capture. /bluewright:capture-global or /bluewright:capture saves whatever you give them verbatim, then walks you through a short, guided conversation about which questions or TODOs are actually worth tracking — never dumping every speculative item it can infer, and never silently overruling an accepted decision it contradicts.
  2. Ask. When you need to think something through, /bluewright:ask answers grounded in what's captured — global and the active investigation together — citing IDs and sources, and saying "not captured yet" rather than guessing.
  3. Make an artifact. When you need to hand something to someone, /bluewright:make-artifact produces it — a doc, a diagram, a summary, an email, whatever fits the ask — flagging anything the record doesn't actually support instead of inventing to fill the gap.
  4. Promote (when something proves out). /bluewright:promote copies a decision, question, or TODO from an investigation into global/, with a back-reference to where it came from. The investigation's own entry is never touched.

5Command reference

Grouped by when you reach for them.

Setting up — once each

/bluewright:init <path>

Creates a workspace: workspace.yml, KNOWLEDGE.md, global/, git init. Asks for team defaults; refuses to nest inside another workspace.

/bluewright:new <slug>

Creates one investigation: the folder structure, the three living files, and your kickoff answers preserved in inputs/00-intake.md.

Capturing

/bluewright:capture-global

The inbox for the workspace's official record. Paste feedback, notes, anything workspace-wide — saves the raw text to global/inputs/, then guides you through which questions/TODOs are worth tracking. Never overrules an accepted decision by itself. Use for anything that's actually official, from any investigation or none.

/bluewright:capture

The same inbox, scoped to the active investigation — not yet official, but promotable. Use whenever new information arrives about this investigation specifically.

/bluewright:promote

Copies selected decisions/questions/TODOs from an investigation into global/, with a back-reference to the source. Never edits the investigation's original entry — a copy, never a move.

Every day

/bluewright:status

One screen: a global-record glance, status, next tasks, open questions (blocking first), latest decisions, sync freshness — plus flags like "artifacts older than your newest decision". Read-only, changes nothing. Start your day here.

/bluewright:ask

Interactively analyze what's captured — global and the active investigation together — without changing anything. Cites what it's drawing on every time; says "not captured yet" rather than inventing. Use whenever you need to think something through.

/bluewright:make-artifact

Turns captured information into whatever you ask for — a doc, a diagram, a wiki page, an email, a summary, a presentation outline, anything — grounded in the record, flagging what's thin instead of inventing to fill it. Use whenever you need to hand something to someone.

Watching the outside world

/bluewright:sync

Checks every watchlist entry for changes since the last run — commits in watched repos, updates from watched trackers or wikis — and answers the question that matters: which of my assumptions moved? Breaking changes raise questions against the affected decisions. Runs unattended, so you can schedule it nightly. Run before big steps, or on a schedule.

6A worked example, start to finish

A practical lesson with every command in play. The scenario: external subscriber systems must be notified when an order's status changes, within a minute. Your team owns the order service; the API gateway belongs to another team.

Day 1
/bluewright:init ~/work/platform

One-time workspace setup (skip if your team already has one). You give it the team name and anything worth watching by default (e.g. an issue tracker project key, if that's what your team uses); it creates workspace.yml, KNOWLEDGE.md, and global/, and git-inits the folder.

/bluewright:capture-global

Before any feature work, you record something already official platform-wide: every new service emits change events through the outbox pattern. Saved as D-001 in global/decisions.md — every future investigation can rely on it without re-litigating it.

/bluewright:new order-webhooks

You state the goal — "How do we notify subscribers of order-status changes within 60 seconds?" — link the driving epic or ticket, and put two repos on the watchlist: your order-service clone and the other team's api-gateway. Everything you said lands in inputs/00-intake.md.

Day 2
/bluewright:capture

You drop the integration contract and two meeting notes into the conversation. They're saved verbatim first, then a guided round surfaces exactly two things worth tracking — not a swamp of every ambiguity in the notes: Q-001 "What delivery guarantee do subscribers need?" and Q-002 "Who owns the subscriber registry?". A third candidate ("should retries be exponential?") gets discussed and dropped — too deep, not blocking anything yet.

/bluewright:capture

You paste the product manager's Slack reply. Q-001 gets its answer (at-least-once is fine, duplicates acceptable), and the registry question becomes a task to chase.

Day 3
/bluewright:ask what does this investigation already have to respect?

Read-only sanity check before committing to an approach. The answer pulls in global D-001 (the outbox mandate) alongside the investigation's own record, and points out that a pure polling feed would sidestep the mandate — worth deciding explicitly, not by accident.

/bluewright:capture

You record the approach: webhooks delivered via the outbox, honoring global D-001. Saved as this investigation's D-001, linked to the global decision it follows from.

Day 4
/bluewright:sync

Morning check. The gateway team merged four commits overnight; one renames the event envelope's type field. The impact report says: weakens D-001 — the outbox format assumed the old envelope, and raises Q-003. You re-rule the same day via /bluewright:capture, before an artifact would have shipped the wrong contract.

Day 5
/bluewright:make-artifact a solution design for the architecture review

Grounded in the investigation's record plus global D-001, it writes artifacts/design.md using the solution-design template, plus a context diagram — every claim tracing to a decision or an inputs/ source, with the still-open registry-ownership question called out as a risk rather than papered over.

/bluewright:promote

The webhooks-via-outbox approach held up under review. You promote it: a new global D-002 is written to global/decisions.md, linked back to order-webhooks/decisions.md#D-001. The investigation's own entry is untouched — the next team facing a similar problem now has this as official precedent.

Anytime
/bluewright:status

Between all of the above: a glance at the global record, then one screen for the investigation — status, the top of the to-do list, open questions with blockers first, the latest decisions, and whether anything has gone stale.

7The files, explained

You can open and edit any of these by hand — they're plain text, and the formats are documented in the plugin's docs/spec.md. The essentials, identical whether they live in global/ or an investigation:

decisions.md

One entry per decision: context, the choice, its consequences, links to evidence. Append-only — superseding a decision means a new entry pointing back, so the reasoning trail survives. Status moves from proposed to accepted only when you say so.

questions.md

Each question notes who raised it, and what it blocks. Answered questions stay in the file with their answer — they're part of the record.

todo.md

Four sections: Now, Next, Later, Done. Order inside a section is the priority.

inputs/

Anything goes; nothing here is ever shared directly. Captured material lands here first, verbatim and dated, before being interpreted.

artifacts/

No fixed filenames — whatever /bluewright:make-artifact was asked to produce: a design doc, diagrams as .puml with rendered .png beside them, a summary, an email draft, anything. This is the only folder ever shared outside the workspace.

sync-log.md

One dated section per /sync run — including the quiet ones. Investigation-scoped only. Your morning-coffee review of what moved overnight.

8Staying current while others ship

The systems you design against don't wait for you. The watchlist plus /sync is Bluewright's answer:

  • Put anything that could move under your feet on the watchlist — a local clone of another team's repo, an issue tracker query, a wiki page. Workspace-level entries apply to every investigation; each investigation can add its own.
  • /sync collects what changed since last time, then judges each change against your decisions — not just "4 new commits" but "commit abc123 weakens D-004, which assumed the ledger API is synchronous".
  • It never rewrites your decisions. A broken assumption becomes a flagged question; the re-ruling is yours.
Versions are checked for you Each workspace records the plugin version that created it. A built-in hook checks compatibility on every command — if the plugin is too old for the workspace, it stops and tells you to update; if the workspace's format predates the plugin, it stops and points you at /bluewright:migrate, which is exempt from the check for exactly that reason. Either way you get a clear stop instead of quiet file corruption.

9Ground rules the plugin holds itself to

Your working directory, period

Commands find the workspace by walking up from where you run them. The plugin keeps no global state and never reads or writes outside the workspace — except paths you explicitly put on a watchlist.

Nothing lost, nothing invented

Everything you feed in is preserved verbatim before being interpreted. And no command ever records a decision you didn't make — recommendations arrive as proposed, always awaiting your ruling.

History is append-only

Decision, question, and task IDs are never reused or renumbered. Artifacts regenerate freely; the record they rest on doesn't move. Promotion copies, it never rewrites — an investigation's original entry stays exactly as recorded.

Honest artifacts

/bluewright:make-artifact flags what the record doesn't actually support instead of inventing to fill the gap, and /bluewright:ask says "not captured yet" rather than guessing.
